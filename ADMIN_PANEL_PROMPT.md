# Промпт для ИИ: обновление АДМИН‑ПАНЕЛИ

Ты — опытный фронтенд‑разработчик. Твоя задача — обновить админ‑панель новостного сайта под изменения на бэкенде и исправить связанные баги (например, с полем `featured` / `is_featured`). Админ‑панель — отдельный фронтенд‑проект от основного сайта.

## 1. Кратко о бэкенде (важно для контракта API)

Бэкенд — Spring Boot проект `news-backend`. Ниже только та часть контракта, которая важна для админ‑панели.

### 1.1. Пользователи и авторизация

**Сущность `User`:**

- `username: String` — уникальный логин, используется для входа.
- `name: String` — отображаемое имя пользователя, которое надо показывать в UI.
- `password: String` — пароль (хранится в зашифрованном виде на бэке).
- `role: User.Role` — роль пользователя (например, `ROLE_ADMIN`).
- `isActive: boolean` — активен ли пользователь.

**Поле `email` полностью удалено** из сущности и из бизнес‑логики. Никаких операций по email больше нет, логин идёт ТОЛЬКО по `username + password`.

### 1.2. DTO и ответы для аутентификации

**Запросы:**

- `LoginRequest`:
  - `username: String`
  - `password: String`

- `RegisterRequest`:
  - `username: String`
  - `name: String`
  - `password: String`

- `CreateAdminRequest`:
  - `username: String`
  - `name: String`
  - `password: String`

- `UpdateUserRequest`:
  - `username: String` (опционально)
  - `name: String` (опционально)
  - `password: String` (опционально)
  - `isActive: Boolean` (опционально)

**Ответ пользователя (`UserResponse`):**

- `id: Long`
- `username: String`
- `name: String`
- `role: String`
- `isActive: boolean`
- `createdAt: LocalDateTime`
- `updatedAt: LocalDateTime`

**Ответ логина (`AuthService.login`):**

Пример JSON:

```json
{
  "accessToken": "...",
  "refreshToken": "...",
  "type": "Bearer",
  "id": 1,
  "username": "admin1",
  "name": "Иван Иванов",
  "role": "ROLE_ADMIN"
}
```

— email в ответе отсутствует, есть только `name`.

### 1.3. Статьи (`Article`) и новые поля

Сущность статьи и связанные DTO (`ArticleRequest`, `ArticleResponse`) имеют важные поля:

- `featured: boolean` — флаг избранной статьи (ранее мог называться `is_featured` на фронте, нужно привести к актуальному контракту бэка).
- `authorName: String` — строка, как будет подписан автор на сайте ("Иван Иванов", "Редакция" и т.п.). Не обязана строго совпадать с `User.name`.
- `scheduledAt: LocalDateTime` — дата и время, когда статья должна автоматически опубликоваться в будущем.

Логика на бэке:

- Если `request.scheduledAt` **не null** и строго **в будущем**:
  - статья сохраняется как **не опубликованная** (`published=false`),
  - `scheduledAt` сохраняется и есть фонова0ая задача, которая опубликует статью в указанное время.
- Если `scheduledAt` **null**:
  - публикация определяется полем `request.published` (`true/false`).
- `featured` всегда читается из запроса (`request.isFeatured()` / `featured`).

`ArticleResponse` в ответах админ‑панели уже содержит:

- `featured: boolean`
- `authorName: String`
- `scheduledAt: LocalDateTime`

## 2. Что нужно сделать в админ‑панели

Ниже список задач, которые нужно выполнить в существующем фронтенд‑коде админ‑панели.

### 2.1. Аутентификация (login/registration)

1. **Удали любую логику, связанную с email:**
   - Не должно быть полей/form‑контролов email в формах логина/регистрации/создания админа.
   - Не должно быть передачи email в запросах.

2. **Форма логина:**
   - Поля: `username`, `password`.
   - Запрос к бэкенду: `POST /api/auth/login` (или фактический путь из проекта) с телом:
     ```json
     { "username": "...", "password": "..." }
     ```
   - Обнови обработку ответа так, чтобы сохранять `accessToken`, `refreshToken`, `id`, `username`, `name`, `role`.

3. **Форма регистрации (если есть в админке):**
   - Поля: `username`, `name`, `password`.
   - Тело запроса: `{ "username", "name", "password" }`.

4. **Создание админа:**
   - Найди форму/модалку/страницу для создания администратора.
   - Поля формы: `username`, `name`, `password`.
   - Тело запроса: `{ "username", "name", "password" }`.
   - Удали любое упоминание email (в валидации, плейсхолдерах, мапперах запроса и т.д.).

5. **Отображение текущего пользователя в UI:**
   - В шапке/меню/профиле используй `name` из ответа логина (если `name` пустое, можно показывать `username`).
   - Убедись, что нет использования email для подписи пользователя.

### 2.2. Управление пользователями

1. **Список пользователей:**
   - При запросе списка пользователей используй контракт `UserResponse` без email.
   - В таблице/карточках пользователей показывай колонки:
     - `username`
     - `name`
     - `role`
     - `isActive`
     - `createdAt`
     - `updatedAt`
   - Удали колонку email, если она есть.

2. **Редактирование пользователя:**
   - Форма редактирования должна работать с `UpdateUserRequest`:
     - `username` (опционально)
     - `name` (опционально)
     - `password` (опционально)
     - `isActive` (опционально)
   - При сохранении:
     - Отправляй только действительно изменённые поля, либо корректно формируй объект с этими полями без email.
   - Удали все следы поля email (формы, интерфейсы/типы, проверка уникальности и т.д.).

### 2.3. Статьи: featured / автор / расписание публикаций

1. **Формы создания/редактирования статьи:**
   - Найди все формы (обычные JSON и multipart c загрузкой изображений).
   - Убедись, что в форме есть и корректно связаны с состоянием:
     - `featured: boolean` (чекбокс "Сделать избранной" или аналогичный переключатель).
     - `authorName: string` (поле ввода, как автор будет показан на сайте).
     - `scheduledAt: datetime` (датапикер + таймпикер или аналогичный контрол). Поле опциональное.
     - (опционально) `published: boolean`, если в UI есть переключатель "Опубликовано".

2. **Отправка на бэкенд:**
   - Для JSON‑эндпоинтов убедись, что запрос содержит правильные имена полей:
     - `featured`
     - `authorName`
     - `scheduledAt`
     - `published` (если используется)
     - + остальные текущие поля (`title`, `content`, `categoryId`, и т.п.).
   - Для multipart запросов (с изображениями):
     - Передавай `featured`, `authorName`, `scheduledAt` как отдельные поля `FormData` с ИМЕНАМИ, которые ожидает бэкенд (в контроллере это именно `featured`, `authorName`, `scheduledAt`).

3. **Фикс бага с `is_featured` / `featured`:**
   - Проверь, что во всём фронтенд‑коде админки используется **одно** актуальное поле, соответствующее тому, что приходит с бэка (`featured`):
     - В типах/интерфейсах статьи.
     - В рендерах таблиц и карточек.
     - В фильтрах/сортировках по избранным.
   - Если где‑то используется `is_featured` или другое имя — приведи к `featured` (или к тому, как это реально называются в `ArticleResponse`).
   - Тест руками (через DevTools → Network):
     - Создай статью с `featured = true` и проверь, что в запросе поле уходит правильно.
     - Убедись, что в ответах статья имеет `featured = true` и в списке админки она отображается как избранная.

4. **Планирование публикации (`scheduledAt`):**
   - В UI добавь/проверь контрол для выбора даты и времени (можно использовать существующий компонент).
   - Логика отображения в админке:
     - Если у статьи `scheduledAt` в будущем и `published = false`, помечай её как "Запланирована на <дата/время>" (например, отдельный статус/лейбл).
     - Если `scheduledAt = null` и `published = true`, показывай как обычную опубликованную статью.
   - При редактировании статьи:
     - Не затирай `scheduledAt` случайным образом (например, не посылай `null`, пока пользователь явно не убрал дату).

### 2.4. Общие баги и чистка кода

Пройдись по коду админ‑панели и:

- Удали оставшиеся упоминания `email` (поля форм, валидация, отображение, типы/интерфейсы, утилиты).
- Убедись, что:
  - Все запросы на бэк используют актуальные поля (`username`, `name`, `featured`, `authorName`, `scheduledAt`).
  - Нет падений UI, если `name` отсутствует (в этом случае можно отображать `username`).
  - Ошибки валидации и ответы `400 Bad Request` от бэка корректно показываются в админке.

### 2.5. Проверки после изменений

После всех правок:

1. Проверь сценарий логина:
   - Войти с `username + password`.
   - Убедиться, что в шапке/профиле отображается `name`.

2. Проверь сценарий создания админа:
   - Создать нового админа с `username + name + password`.
   - Проверить в списке пользователей, что отображаются `username`, `name`, `role`, `isActive`.

3. Проверь работу статей:
   - Создать статью с `featured = true`, убедиться, что она помечена как избранная в списке.
   - Создать статью с будущим `scheduledAt` и `published = false`, убедиться, что она отображается как "запланирована".
   - Отредактировать существующую статью, изменить `authorName` и проверить, что новый текст уходит в запрос.

Ориентируйся на существующую архитектуру фронтенда (React/Vue/другое), не ломай её, а адаптируй под описанный контракт бэкенда и исправь связанные баги.
